Outil monitoring

Supervision Alertes Diagnostic

Contexte détaillé

Objectif du projet

L'objectif était de centraliser des informations de supervision pour réduire le temps de diagnostic lors des incidents applicatifs. Le projet devait afficher les services critiques, leur état, les alertes remontées et les premiers éléments de contexte utiles au support.

Enjeu métier

Gain recherché

En regroupant les données essentielles dans un seul tableau de bord, l'équipe peut mieux prioriser les incidents, communiquer plus vite et éviter la dispersion entre plusieurs outils de suivi.

Diagramme de classes

Le service, l'alerte et le responsable forment le noyau d'information affiché au support.

Architecture MVC

Le dashboard consolide les métriques issues du modèle via un contrôleur orienté diagnostic.

Extrait de code 01

Consolidation des alertes

Le regroupement par service facilite la lecture et évite les doublons d'affichage.

const alertsByService = alerts.reduce((accumulator, alert) => {
  const bucket = accumulator[alert.serviceId] || [];
  bucket.push(alert);
  accumulator[alert.serviceId] = bucket;
  return accumulator;
}, {});

Extrait de code 02

Code couleur de criticité

La criticité est normalisée pour rendre la grille immédiatement compréhensible par l'équipe.

function getSeverityBadge(level) {
  return {
    critical: "Rouge",
    warning: "Orange",
    info: "Bleu"
  }[level] || "Neutre";
}

Extrait de code 03

Filtre par périmètre

Le filtre permet d'isoler rapidement une famille d'applications au moment de l'analyse.

const filteredServices = services.filter((service) => {
  return activeScope === "all" || service.scope === activeScope;

Résultats et bilan

Bilan du projet

Ce projet a renforcé ma capacité à synthétiser des informations techniques pour des usages opérationnels. J'y ai travaillé la lisibilité des données, la priorisation visuelle et la valeur d'un outil bien calibré pour le support.

Sprints du projet

Organisation Scrum Agile

Sprint 1: cadrage du besoin, decoupage des user stories, priorisation du backlog et definition des criteres d'acceptation.

Sprint 2: developpement des fonctionnalites principales, points quotidiens (daily), integration continue et corrections des blocages.

Sprint 3: tests, stabilisation, revue de sprint avec demonstration, puis retrospective et plan d'amelioration pour la suite.
